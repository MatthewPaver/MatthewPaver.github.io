RAG Regression Gate: keep the right policy within reach

A search update puts an old, unapproved proposal above the current staff policy. RAG Regression Gate compares the sources found before and after the update so a team can investigate before releasing it.

Explore RAG Regression Gate Technical evidence Inspect the source

The problem

An internal help assistant depends on finding the right documents. A search update can change which policy it finds first, even when every question still finds some relevant evidence. Staff could then receive an answer based on an outdated proposal.

The decision it supports

The before-and-after view makes that hidden change inspectable. In the synthetic example, the approved retention policy says 30 days; an old 365-day proposal overtakes it after the update. All six question checks still pass, while overall source order worsens. The gate holds the update for investigation.

Limits

The website explores two saved Python comparisons. It does not run a live assistant, accept uploads or prove generated answers correct. Its six-question examples use threshold-only checks and are smoke tests, not an accuracy benchmark. Engineers must run the command-line tool on representative questions for their own documents. A passing result does not prove an improvement.

Independent public project by Matthew Paver. Examples are synthetic. No client deployment, adoption, time saving or measured commercial benefit is claimed. User comprehension has not yet been measured.

Complete journey

  1. Explore the held update. Compare the approved policy and old proposal before and after the search change.
  2. Review all six staff questions and open the source documents. The hold applies to the overall update; another question may show no new drop.
  3. Switch to the saved unchanged comparison. Read the HTML report or download the exact JSON result for either comparison.
  4. For your own documents, follow the repository setup and run the gate on labelled questions. The website demonstrates the evidence an engineer can produce.

Why the design changed

Before, the report opened with technical scores. After, a staff question, the release decision and the source comparison come first. Visitors can inspect six questions, compare a second saved result and choose a readable report or the exact JSON data.

Technical evidence

The website keeps the saved reports, input fingerprints, configurations and source text inspectable. The separate SciFact benchmark below uses 5,183 abstracts and 300 test questions. Benchmark results describe one public dataset, not staff-policy accuracy or user benefit.

Trade-offs

  • Significance costs power. On a six-question fixture a real one-question regression reads as noise, so the small fixture in CI runs threshold-only as a tripwire.
  • Passing is not improving. The dense MiniLM model passes because its drop is within noise, yet every point estimate is negative. A threshold-only gate would have failed it on MRR. If a change must prove it is better, read the significance verdicts, not the pass.
  • Deterministic over clever. No LLM judge and no generator in the loop: the gate is free to run on every pull request and gives the same answer twice.
How the release check works

Baseline and candidate search configurations use the same labelled questions. A metric fails when its drop exceeds the practical threshold (0.02 absolute by default) and a 95% paired bootstrap interval excludes zero. The small synthetic examples disable bootstrap checks. Build time, latency and memory are reported, not gated. No language-model judge or answer generator is involved.
